Remote Hosts for Synara

Run agent sessions on other machines (VPS, Mac Studio) over SSH. Sessions survive laptop sleep, phones connect directly, no hosted infrastructure required. Validated against the codebase with a multi-agent review pass: 6 deep-dives, 3 adversarial critiques, 1 synthesis.

The idea in one screen

A remote environment is a full Synara server on the remote box. The local server is an SSH broker and byte-level proxy. The browser keeps one origin. The phone connects directly.

What you get

  • Composer picker: "Start in: Local / worktree / VPS / Mac Studio", exactly like Codex's cloud picker.
  • Sessions outlive the laptop: threads, terminals and git live on the remote server, supervised by systemd/launchd.
  • Phone access with zero cloud: the remote is a normal Synara server serving its own web bundle. Tailscale + QR pairing, done.
  • Fork-friendly: everything self-hosted; artifacts ship as GitHub Release assets.

Why this shape

  • Codex, OpenCode and T3 Code all converged on "persistent server on the remote, thin client". Nobody syncs files.
  • Making Synara's ~9 provider spawn paths + PTYs + git remote-aware one by one (the Codex per-session model) was evaluated and rejected: a permanent 2x testing tax.
  • The relay is byte-level, never RPC-aware: the WS surface has ~100 methods, no routing key, and weekly contract churn.
  • Validation surfaced 3 real bugs in main that get fixed first, as standalone PRs (Phase 0).

The scenario that motivates everything

Start a long-running session on the VPS from the laptop at 6pm. Close the laptop. Open the phone at 11pm over Tailscale, watch the turn finish, answer one approval, go to sleep. Reopen the laptop at 9am: the thread is right there in the sidebar, done. Nothing on the laptop mattered after 6pm.

Lesson from Codex

Bootstrap fragility (login-shell PATH) is their #1 community complaint. Hence: upload-first with pinned Node, absolute paths everywhere, structured probe errors instead of a spinner.

Lesson from T3 Code

SSH as a launch helper, not a transport protocol, keeps the final hop plain WS and the codebase untouched. They rejected Zed's custom proxy protocol deliberately. So do we.

Lesson from OpenCode

Their planned SSH feature (#7790) is exactly this shape. Their headless-approval hang (#16367) and remote worktree bugs told us which failure modes to design for up front.

Architecture

Two access paths to the same remote server: brokered through the laptop (single origin) and direct from the phone (Tailscale). The remote server is authoritative for everything it owns.

Why the proxy is byte-level

  • The WS surface is one flat RpcGroup, ~100 methods, no environment routing key.
  • Event sequences are per-server SQLite AUTOINCREMENT: mixing two servers' streams collides. Aggregation stays client-side, keyed by environmentId.
  • contracts/rpc.ts churns weekly; a method-aware relay would break on every release. Byte-forwarding means the browser speaks each server's exact schema.

But not literally dumb

  • Cookie hygiene: strips Cookie/Set-Cookie both ways across /env/*; injects its own bearer/ws-token. Otherwise the remote's cookie clobbers the local session on the shared origin.
  • Flow control: pauses upstream on backpressure, never drops frames (terminals are lossless), closes on ceiling breach with bounded memory.
  • Fail-fast liveness: upstream dial completes before the browser upgrade is accepted; dead tunnels tear down all proxied connections so the client's snapshot-on-subscribe recovery fires.

Design detail

Every decision below survived the adversarial pass. Expand what you care about.

bootstrap Upload-first bootstrap, VS Code model ›
  • Probe: uname -sm + existing state → structured readiness report (runtime, pidfile/port, node-pty, provider CLIs) rendered in the environment UI. Never a bare "connection failed".
  • Pinned Node ≥22.19 provisioned to ~/.synara/remote/node/<v>/ if missing; server tarball (bundled server + web client) uploaded via scp at the broker's exact version. Remote internet download is opt-in.
  • node-pty smoke gate; if it fails to build, terminals disable as a capability flag instead of failing bootstrap.
  • Artifacts: GitHub Release assets per arch (darwin-arm64, linux-x64, linux-arm64). Bare npm name synara is squatted; scoped package if npm at all.
  • SSH auth: agent or passphrase-less keys required and explained; host-key fingerprint confirmed explicitly in the add-host UI; ProxyJump/2FA via ~/.ssh/config + "Test connection".
lifecycle OS supervisor owns restarts, not pidfiles ›
  • systemd user unit + loginctl enable-linger on Linux; launchd LaunchAgent (RunAtLoad+KeepAlive) on macOS. The broker is only a fallback restarter.
  • Pidfile-only dies on reboot, which kills the "laptop closed, phone still works" promise. Supervisor is what makes the promise real.
  • No-auto-exit policy: the remote never self-exits while threads exist. Remote logs at ~/.synara/logs with a "view remote logs" affordance (VS Code's #1 troubleshooting complaint is the real error hiding behind a spinner).
  • Honest UI copy: a remote restart interrupts in-flight turns; they reconcile to interrupted exactly like local semantics.
auth Pairing & enforcement with zero hosted infra ›
  • Policy-driven enforcement: remote-reachable bind or broker-managed mode ⇒ session auth on every WS upgrade and HTTP route, no legacy-token bypass. (Today the socket is unauthenticated whenever --auth-token is unset. That is fixed first.)
  • Pairing client: a /pair route reading the credential from location.hash, an auth-gate token form as fallback, and "Pair a device" in settings that mints a token on the remote via the relay and renders a locally generated QR. T3 needs app.t3.codes for this; we don't.
  • Broker handshake: launcher seeds a single-use owner grant → broker exchanges for a labeled bearer (stored in local secretsDir) → per-connection ws-token → re-pair over SSH on 401.
  • --trusted-origin for the tailscale serve HTTPS origin; Secure cookies on HTTPS; guard the three bare crypto.randomUUID() call sites for plain-HTTP fallback.
versioning Pin to broker; never auto-restart a busy remote ›
  • Side-by-side installs under ~/.synara/remote/versions/<v>/; one server per host SYNARA_HOME; version is a host-level property with a relaunch lockfile.
  • First RPC after tunnel-up fetches the descriptor. Mismatch ⇒ hard-reject into a first-class version-mismatch state: read-degraded (view threads, no new dispatch).
  • Relaunch is user-invoked, blocked while turns are active (or explicit "interrupt N turns" confirm). Weekly releases × auto-restart would routinely destroy the long-running work this feature protects.
  • Newest-wins, human-confirmed: an older broker never downgrades a newer server; it prompts to update itself.
client Environment-keyed client, "Start in" picker, deep links ›
  • wsNativeApi/wsTransport refactor from module singleton to an environment-keyed registry behind React context; one shell snapshot + sequence watermark per environment, merged at render.
  • environmentId rides thread creation but never enters the orchestration command schema; routing is which per-environment NativeApi instance receives the dispatch.
  • Two-stage picker: environment → that environment's projects (existing local/worktree option per project). Cold-host onboarding: pre-filled remote terminal (git clone, gh auth login, provider logins) + "create project from repo URL".
  • Deep links gain the environment dimension (/env/:envId/:threadId, legacy defaults to local) + a persisted threadId → environmentId map; unreachable environments render as connectivity state, not a 404.
  • Per-environment provider badges from the remote's ProviderHealth stream.
prereq Bugs in main found during validation (Phase 0 PRs) ›
  • Auth bypass: WS served unauthenticated when no --auth-token set; remote-reachable bind = open RCE. Fix: policy-driven enforcement.
  • Pairing client missing: server side exists, no /pair route / token gate / QR anywhere in the client.
  • Approval race: decider.ts accepts thread.approval.respond without a pending check; two devices answering once each appends contradictory events. Fix: first-wins at the event log, benign "already answered" for the loser.

Failure modes, walked through

The design is judged by its worst days, not its demo. Pick a scenario.

Laptop sleeps while a remote turn is running

  1. SSH tunnel drops. The remote server and the in-flight turn don't notice or care; nothing in the turn lifecycle requires a client connection.
  2. Broker keepalive (ServerAliveInterval + WS ping deadline) declares the environment down and tears down all proxied connections for it, so nothing goes silently stale.
  3. The environment shows reconnecting via the environment.status push; per-connection errors are not the UI's source of truth.
  4. On wake, the broker re-establishes SSH; the proxy completes the upstream dial before accepting browser upgrades (no connect-then-fail storm), with jittered backoff.
  5. Relayed subscriptions resubscribe and the remote re-sends full snapshots. No relay-side buffering, no cursors, nothing to corrupt. The finished turn is simply there.

The VPS reboots overnight

  1. SQLite event log, resume cursors and thread projections persist on the remote disk.
  2. systemd user unit (with linger) / launchd restarts the server at boot. The broker is only a fallback restarter.
  3. Startup reconciliation marks turns that were in flight as interrupted, identical to local restart semantics. The UI says so honestly.
  4. Phone and laptop reconnect to a healthy server with full history. Provider sessions resume via their native resume cursors on next turn.

Local Synara updated, remote still on last week's version

  1. First RPC after tunnel-up is a descriptor fetch; serverVersion mismatch hard-rejects the proxy session. No partially-working schema mismatch, ever.
  2. Environment enters version-mismatch: read-degraded, threads visible, no new dispatch. "Remote is v0.5.1, update required."
  3. Upgrade is user-invoked and blocked while any thread has an active turn (drain-then-upgrade), or requires an explicit "interrupt N turns" confirmation.
  4. An older broker never downgrades a newer server; it prompts to update itself instead. Phone-direct is immune throughout: the remote serves its own matching web bundle.

Phone approves, laptop denies, same approval

  1. Both responses race to the remote's event log (one via direct Tailscale, one via the relay).
  2. The decider consults the pending-approval read model: first write wins at the event log, the second is rejected with a typed already-resolved error.
  3. The losing device shows a benign "already answered on another device". This decider fix lands in Phase 0 because the race exists locally today too.

Host configured but unreachable

  1. Per-host connection policy (default on-demand) means no N-tunnel fan-out storm on every app launch or wake.
  2. The host renders from local config as a quiet "offline — tap to connect" row with a connectivity badge. No recurring toasts.
  3. Its thread list appears only while connected; the local server never caches or mirrors remote read models.
  4. Deep links into that environment render "lives on vps-1, reconnecting" as the loading state instead of a 404.

Phasing

Four phases, each independently valuable and shippable. Nothing depends on a big-bang merge.

PHASE 0

Standalone fixes ships alone · small PRs

  • Policy-driven auth enforcement (fixes the unauthenticated-socket gap in main)
  • Pairing client: /pair route, auth-gate, locally generated QR
  • --trusted-origin, Secure cookies, randomUUID guards
  • Approval idempotency at the decider
  • Publish server tarball as a GitHub Release asset

Every item is a real bug or missing feature today, remote hosts or not.

PHASE 1

Connect to a remote by URL proves the multi-server model

  • Environment-keyed wsNativeApi/wsTransport registry (series of small PRs)
  • Descriptor handshake, version-skew detection, version-mismatch UI state
  • Client-side aggregation keyed by environmentId; environment-aware deep links
  • "Add server by URL + token" in settings. No SSH, no broker.

This alone is the OpenCode model and already useful to anyone running Synara on a box.

PHASE 2

SSH broker + bootstrap + supervisor

  • Host config, probe with structured readiness report, host-key confirm UI
  • Upload-first bootstrap, pinned Node, node-pty gate, side-by-side versioned installs
  • systemd/launchd supervisor, remote log surfacing
  • Provisioning handshake, connectivity state machine, per-host connection policy
PHASE 3

Single-origin relay + polish

  • /env/:envId/* sanitizing, auth-injecting, flow-controlled byte proxy
  • Two-stage "Start in" picker, cold-host onboarding, per-project defaults
  • Provider badges per environment, tailscale serve detection, multi-host QR screen
  • Load test: fast remote terminal against a slow browser consumer

If the relay ever proves troublesome, Phase 2's port forward already enables direct-to-forwarded-port as a fallback.

Open questions for the maintainer

The genuinely contestable calls. Everything else in the proposal I'm confident defending.

1 · SYNARA_HOME sharing model
One shared home per remote box (unified thread store, phone sees everything, but version becomes a contended host-level property across brokers) versus one per broker identity (no contention, but the shared Mac Studio's thread store forks). Proposal defaults to shared; which do you want?
2 · Busy remote on an old version
Read-degraded until the user drains and upgrades, or should the broker surface the remote's direct URL so an out-of-date-but-busy remote stays fully usable until idle?
3 · Scope ownership
The full design is a 4–8+ week arc and SSH bootstrap is the highest support-burden tier. Comfortable with incremental external contribution starting at Phase 0/1, gating the broker tier on those proving out?
4 · macOS headless setup
Mac Studio as a host needs one-time manual steps (auto-login or LaunchDaemon, Full Disk Access for sshd). Document rather than automate in v1?
5 · Publishing
GitHub Releases only (fully self-hosted, fork-friendly) or also a scoped npm package? Bare synara on npm is squatted either way.
6 · Tailscale positioning
Bless tailscale serve as the recommended phone path (best UX, third-party dependency) with SSH port-forward as the always-works fallback, or keep Tailscale strictly optional?
